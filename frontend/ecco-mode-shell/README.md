# ECCO Mode Shell

A dependency-free, **read-only** Home Assistant Lovelace card that gives one view **two presentations of the same data**
behind one polished switch:

- **Production Mode**: calm and simple. The view's own cards, one plain-language sentence, the alert strip.
- **Geek Mode**: every available non-secret data point of the view (every sensor, attribute, diagnostic, timestamp, derived
  value, assumption, limit, code and provenance), grouped, collapsible, searchable, filterable and paged, with update ages,
  source ids, descriptions, units, a redacted raw attributes view and copy / export of non-secret diagnostics.

This is the **first offline proof**, built for the ECCO Intelligence SHADOW view (contract `ecco-intel-entities/1`). Status:
source only, run against synthetic fixtures. Nothing here is installed, registered or connected to Home Assistant, and nothing ran in
a real Home Assistant. Licence: GPL-3.0-or-later; no third-party code.

## The mode is a presentation toggle, nothing more

- It is **not** ECCO's Manual / Assisted / Automatic authority. Switching it never starts or stops Intelligence, never enables
  ASSISTED or AUTONOMOUS, never alters Manual control authority, never writes a register or helper, never cancels an armed
  session and never calls a service. The shell reads `hass.states` (plus `hass.locale` and `hass.themes` for formatting) and
  nothing else of `hass`.
- It lives **only in the element instance**: Production on first render and on every reload; reset to Production when the element
  is connected, when it is disconnected, when the location moves away from the path it was entered on (`location-changed`), on
  `pagehide`, and when the element becomes hidden (its box goes 0 x 0). A switch in one view never changes another view. It is
  never stored: no `localStorage`, `sessionStorage`, IndexedDB, cookie, history or URL state.
- **Safety-critical alerts, recovery state and owner-action-needed status stay visible in both modes.** They come from the
  catalogue's `alerts` list through one function (`deriveAlerts`) and are drawn by one function (`renderAlertStrip`) into a strip
  that sits **outside** both switchable bodies. A condition that cannot be checked (entity unavailable, unknown, missing, or
  attribute absent) is shown as "Cannot check this right now", never as silence. The strip is the same for a screen reader in both
  modes: a labelled `region` that is announced politely (`aria-live="polite"`), its alerts `role="alert"` (critical) or `role="status"`,
  and nothing in the shell ever sets `aria-hidden`, `inert`, `hidden` or a different role or `aria-live` on it or around it
  (pinned in the source, compared in both modes by the element tests and by the browser check; see "Tests").
- Geek Mode adds **no** permission: it shows, it offers no control and no installer-only write, and it bypasses nothing. The only
  things it can do besides read are: dispatch the standard `hass-more-info` event (open an entity) **for an entity of a read-only
  domain only** (sensor, binary sensor, event), write to the clipboard on a button press, and offer a Blob download on a button press.
  The dialog Home Assistant opens for any other domain has write controls (a slider, a toggle, Run, Install), so the `hass-more-info`
  event itself is a write path for those domains. Geek Mode therefore never opens such a dialog: its row offers **Copy entity id**
  instead, and says why. (Even a read-only domain's dialog has Home Assistant's own entity Settings tab for administrators; that is
  Home Assistant's permission model, not an ECCO control.)

## Same data, one adapter

`buildSnapshot(states, catalogue, nowMs)` is the single adapter. The alert strip, the Production summary, the Geek header counts,
the instrument tiles and every row read the **one snapshot** built from the one `hass` object; the child cards receive that very
same `hass` object. Per-state-object caching means a change to one entity recomputes one row and re-renders one row.

**Updates.** Home Assistant sends a new `hass.states` for any change anywhere in the house. The shell rebuilds only when something it
reads changed: the state object of one of the entities of the last snapshot (its sources, its discovered entities, its alert entities)
or the number of entities. Every row whose state object is unchanged is reused (within one second of the clock it was built at, because
its age moves, and only while a fresh classification still gives the status the row carries: a row built just before `stale_after_s` turns
STALE on time; only its age text may lag, by less than a second). A burst of relevant updates is taken eight at a time per 500 ms; the rest is coalesced into ONE rebuild at the end of the
burst, by the one timer slot that also runs the 15 s age tick (the slot is re-armed for the flush and goes back to the tick when it fires;
nothing else is a timer). During such a burst the child cards still get every `hass` at once while the shell's own snapshot (Geek rows,
Production summary, alert strip) catches up at the end of the burst: the two can differ for up to about 500 ms. A theme change is applied at once, whatever the states did.

## Honest inventory

Every data point has exactly one status, said in **words and with an icon**, never colour alone (and with a distinct border
style):

| Status | Meaning |
|---|---|
| Live | a value is reporting and, if the source has a freshness limit, it is within it (sources without a limit say "age not monitored") |
| Stale | older than the catalogue's `stale_after_s`; shown for reference, never as current |
| Unavailable / Unknown | Home Assistant says so; **no value is shown** |
| Not measured | the catalogue lists it but Home Assistant has no such entity; **nothing is invented** |
| Simulated | the source marks it simulated: a `simulated`, `is_simulated` or `synthetic` flag, or a `provenance`, `data_source` or `source_kind` that starts with simulated, simulation, synthetic, fixture, mock, demo, sample, fake or dummy (any case). Nothing else is guessed at |
| Unverified | the source says so (`verified: false`, `provenance_ok: false`, `provenance: UNVERIFIED`), or it has a freshness limit but no usable timestamp, or its timestamp is more than five minutes AHEAD of the clock (clock skew: no age is invented, and it is never "just now") |

A declared attribute that is absent is listed as "Not present". Attributes the catalogue does not know about are listed too (the
card tolerates unknown extra keys), and the first nesting level of a dict attribute is listed as sub-rows (deeper levels are in the
raw view).

## How the alert conditions are read

The catalogue's `when` has six forms. The shell reads them exactly as `docs/product-ui/PRODUCTION_GEEK_MODE.md` section 3.1 documents, and
`test/real-catalogue.test.mjs` pins every reading:

| Form | Fires when | When the entity cannot be read |
|---|---|---|
| `{state_in: [..]}` | the state is in the list, including a listed `unknown` or `unavailable` | "cannot check" line |
| `{state_not_in: [..]}` | the state is not in the list, or the entity is down | fires |
| `{unavailable: true}` | the state is `unavailable`, or the entity is missing from `hass.states` | an `unknown` state is a "cannot check" line, not this alert |
| `{attribute: a, in: [..]}` | the attribute equals an entry strictly or as text (the list may mix `false`, `"false"` and `"False"`) | "cannot check" line (also when the attribute is absent) |
| `{attribute: a, not_in: [..]}` | the attribute is present and is **not strictly** one of the entries (no text matching: the text `"true"` is not the boolean `true`; no case folding) | "cannot check" line (also when the attribute is absent) |
| `{state_outside: [..]}` | the state is up (not `unavailable`, not `unknown`, not missing) and is none of the listed words | "cannot check" line (another alert says the entity is down) |

An alert that already says an entity is down (an `unavailable` alert, or a listed `unknown` / `unavailable` state) replaces the
"cannot check" lines for that entity, so one failure is one line. `in` and `not_in` together are refused (the alert is dropped and the
catalogue reports it).

**The watchdog coupling.** In a real Home Assistant the package watchdog template turns OFF when the status entity says a mode other
than SHADOW, an `applies_nothing` that is not strictly the boolean true, a contract version it does not know, or a status word the
contract does not define, and a watchdog that is off is only a warning. The offline strip therefore raises its own lines from the status
entity itself: `mode_not_shadow`, `applies_nothing_not_true`, `contract_mismatch` (critical) and `status_unrecognised` (warning), next to the
existing `applies_nothing_false` (which names the values false, "false" and "False"; the two together cover every value but the boolean true,
and no value raises both). `test/fixtures/intelligence.states.contract-breach.json` is the case the earlier fixtures did not model: the
status says ASSISTED, its state is OK and the watchdog is on.

## Nothing secret is surfaced

Replaced by a **withheld marker** (an icon and the word) in rows, raw view, search index, copy and export: values under keys such
as token, password, secret, api key, authorization, bearer, credential, private key, webhook, cookie, session; latitude,
longitude, location, address, e-mail, serial, MPAN; a compound key name that ends in a key word (`encryption_key`, `wifi_key`,
`license_key`, `sshKey`), a compound key name that ends in a login word (`mqtt_user`, `db_login`, `serviceUser`; a bare `user` is shown),
`pin` and `psk`, even for a short value; a compound key name that ends in `pass` (`wifi_pass`, `mqttPass`; **a bare key named `pass` is shown on purpose**: it is also the
word for a passed test, so a value under it is not withheld by the key rule, though a quoted `"pass": "..."` pair inside a string is), `pw` in any
position and the compact `wifipass` and `wifipw`; webhook paths (the id in the path is the credential), under any key; JWT-like strings, long hex and base64 blobs, URLs with credentials or
token query parameters, connection strings, IP and MAC addresses (with colons or dashes, in the dotted three-groups-of-four form, written with a space between the six bytes
(`aa bb cc dd ee ff`, at least one letter), and twelve hex digits with no separator and at least one letter, except under a revision key), coordinate pairs (from three decimals), labelled coordinates (`lat 51.5 lon -0.1`) and hemisphere coordinates (`52.1 N 0.12 W`), the text of a
Wi-Fi QR code (`WIFI:S:...;P:...;;`), a password written as a quoted `pass` or `pw` pair or as `pass=value`,
private host names, URLs whose host is one bare word (`ws://homeassistant:8123`), credential pairs also in JSON or Python form
(`{"token":"..."}`); keys and values are matched on a **folded copy** (invisible and zero-width characters removed, compatibility forms
folded, look-alike Cyrillic and Greek letters turned into Latin), so a secret cannot hide behind them, while what is shown is never the
folded copy; the catalogue's own
`redaction.extra_key_patterns` (for Intelligence: `config_hash`, `entities`, `git_sha`, `latitude`, `longitude`); nested dicts and
lists; key **names** that look secret. The export is passed through the redactor a second time. A public git revision is the one
deliberate exception (a 40-hex git object name is shown only under a revision key). The redaction is a heuristic safety net: it errs
towards withholding (for example a four-part dotted number reads as an address), and the catalogue's `exceptions` list is where a
source is excluded on purpose. What it does NOT catch is listed honestly in sections 15.3 and 16.4 of the design document (for example a coarse
degrees-minutes-seconds position, a phone number, a post code, a chat-bot token inside a URL path, a compact word such as `wifipassword`, a prose sentence such as
`mqtt pass hunter22`, `p@ss: hunter22`, a `0x` hex literal of a MAC address and an all-digit MAC address written with spaces, which cannot be told from six numbers).

Every string is read **whole** (up to a hard bound of 20000 characters) and only then cut for display at 4000, with the cut said: a secret that crosses the display cap, or lies wholly beyond it,
withholds the whole text, and a text longer than the bound is withheld without being read in part (review round 6; the tests sweep every kind of secret over every offset that matters of texts
of 1500 to 20000 characters, on every path, section 18.3 of the design document). The catalogue's key patterns are **plain fragments** (`[a-z0-9_]{1,80}`, at most 40) matched as a part of a
key name, in windows of 200 characters that overlap, so every part of a key is read and no expression is ever built from a catalogue; a pattern that is not a plain fragment is a catalogue
error that the strip shows, never a silent drop, section 18.5.

## Use

```yaml
type: custom:ecco-mode-shell
view_id: intelligence
title: ECCO Intelligence
catalogue: !include ../catalogue/intelligence.catalogue.json   # inline data; the card fetches nothing
page_size: 25                                                  # optional, 5 to 100
allow_custom_cards: []                                         # optional: custom cards (by name) the dashboard author has checked are read-only
always:                                                        # shown in BOTH modes: must be read-only
  - type: custom:ecco-intelligence-card
production:                                                    # shown only in Production Mode, passed through unchanged
  - type: tile
    entity: input_boolean.ecco_intel_paused
    tap_action: { action: toggle }
    icon_tap_action: { action: toggle }
```

`examples/intelligence-modes.yaml` is the full example: it wraps the **existing** ECCO Intelligence card, its watchdog / status
entities card and its pause tile **unchanged** (`test/test_example_dashboard.py` proves they are equal to the existing dashboard's, that
the include resolves to the real catalogue and that a YAML loader reads that file exactly as a JSON loader does).

**The `always` guard.** `validateChildCards` is an **allowlist**. A card in `always` must be one of: markdown, entities, glance, the
history graph, the statistics graph, sensor, gauge, entity, heading, tile, or a stack, grid or conditional of such cards (checked
inside too); a card's header or footer may only be a graph or a picture; a custom card must be on the shell's default list
(`custom:ecco-intelligence-card`, pinned read-only by its own test suite) or be named by the dashboard author in `allow_custom_cards`
once checked. Everything else is refused with a visible notice and a shell alert: many cards carry an implicit write that no action key
shows (a picture-glance card toggles its entities by default, an area card shows toggle buttons, a custom button card taps to toggle, a
buttons footer toggles). On top of that, any `always` card that carries an
action other than `none`, `more-info` or `navigate`, a service-call shaped key, a write-capable type (button, light, thermostat,
iframe ...), an entities row of a writable domain, a heading badge on a writable domain without an explicit safe `tap_action`, or a tile
on a writable domain without explicit safe actions is refused. Cards in
`production` are **not** filtered: that is where controls live, and they keep exactly the permissions they have today (the shell
passes the very same configuration object). Consequence, flagged for the owner: **Geek Mode hides the pause tile** (it only
shows); a control stays one tap away in Production, and Geek Mode says so. A `more-info` action stays allowed in an `always` card (the
agreed interface), but on a writable entity it opens a dialog with write controls: the example has none, and it is an owner decision
whether the second tab should refuse it as Geek Mode's own rows now do (design document, section 13).

## The catalogue and the ledger

The catalogue (schema `ecco-geek-catalogue/1`) is produced by the Python side and consumed as data: `groups`, `sources` (stable
ledger `id`, `entity_id`, group, title, description, priority headline / normal / obscure, unit, `expected_update_s`,
`stale_after_s`, origin, attributes with dotted paths into the first nesting level of a dict attribute), `discover` (entity
prefixes, group, exclusions), `alerts`, `exceptions` (secret, privacy, unsupported_source, not_exposed_in_states) and `redaction`.
`validateCatalogue` fails **closed**: an unknown schema or a malformed source switches the Geek inventory off with a visible error
listing each problem, while every individually valid alert still drives the strip. New safe entities with a discover prefix (for
example `ecco_intel_`) appear in the **Discovered** group with no new hand-designed card.

The ledger (`ecco-geek-ledger/1`) lists every source and attribute row (id rule: a source's id, or `<source id>#<attribute name>`),
the honesty states it can take, whether it is withheld, and which fixtures exercise it, then every exception with its reason. The
card and the ledger cannot drift: `catalogueItemIds` returns exactly the ledger's ids, and `test/real-catalogue.test.mjs` renders
the card on every fixture and compares it with the ledger row for row (a card row without a ledger row, a ledger row without a card
row, an attribute present when the ledger says the fixture has it or absent when it does not, the honesty vocabulary, the withheld
values, the exceptions, and the sha256 of the catalogue, the live shape and every fixture).

Regenerate, in this order (the ledger records the hash of the fixtures, so the fixtures come first), and check:

## Browser check of the alert strip (opt-in, review round 3)

The static net reads the stylesheet. The browser check does not: it renders the real card in headless Chrome or Edge and measures what the browser drew for the
alert strip, in Production and in Geek Mode, light and dark, with and without Home Assistant's theme variables, at two card widths in two window sizes. It requires, for
every state and both modes: a strip box with a real size, inside the viewport and inside its card; opacity 1 on the strip and every ancestor; no transform, rotate, scale,
translate, filter, clip-path, mask, backdrop filter or size containment on the strip or any ancestor; no ancestor that clips it; nothing covering the middle of each line;
text and icons at least 12 px, opaque, with at least 4.5 : 1 (text) and 3 : 1 (icon) contrast against what is behind them; and the SAME box with the same lines in both modes.
Since review round 4 it also reads the ATTRIBUTES that decide what a screen reader gets, because pixels cannot show them: no `aria-hidden`, `inert` or `hidden` (of any value) on the strip
or on any ancestor, role `region`, `aria-live="polite"` and a label on the strip, no `aria-busy` or `aria-relevant`, role `alert` / `status` on each alert line, and identical attributes on the strip,
everything around it and every line in both modes. (The browser's own accessibility tree is not reachable from a headless page dump, so the attributes are the evidence.)

```
cls
cd frontend\ecco-mode-shell
node preview\check-strip.mjs                  # check the card as it is (about two seconds)
node preview\check-strip.mjs --selftest       # also prove it is not vacuous: the card passes, 31 deliberately broken copies fail (about one minute)
node preview\check-strip.mjs --card C:\path\to\a-copy-of-ecco-mode-shell.js
```

It looks for Chrome and then Edge in the standard install places (`ECCO_CHROME` overrides). With no browser it prints **SKIPPED** in a banner on both output streams and
exits 0 (3 with `--require`), so a skipped run cannot be mistaken for a pass. It serves the folder on the loopback address only, read only, writes nothing but a temporary
browser profile it deletes, and makes no network request. The judging half (`preview/strip-check-lib.mjs`) is tested offline in `test/strip-check.test.mjs` with synthetic
measurements of strips hidden in every way found so far. The static net stays the mandatory one; this one is run by a person. Since review round 5 the node suites also kill, with no
browser, the five mutants that only this check used to catch (the strip moved inside the shell, an inline custom property set on the shell, a shadow root on the strip), and the mutation runner
hands those five to this check as an extra layer when Chrome or Edge is installed.

## Known limit: a child card shares the shell's style scope

The child cards (the `always` and `production` lists) are mounted inside the shell's own shadow root, in two region elements, so a `<style>` element that a child puts into
its LIGHT DOM (a card without a shadow root of its own) is part of the shell's tree scope and applies to the whole shell, the alert strip included. Neither the stylesheet pin nor
`validateChildCards` can see it: the pin reads the shell's `STYLE`, the guard reads a child's configuration, not its DOM. The cards used today (the ECCO Intelligence card, the pause tile
and Home Assistant's built-in cards) render into their own shadow root, so their styles cannot reach the strip. This was found by reading the code, not in a running Home Assistant.

What holds it today: a custom card in the `always` list must be named in `allow_custom_cards` (the owner's decision per card; the `production` list is not filtered, because that is where
controls live, so a style element there is held by review of the dashboard configuration alone), and the browser check
(`preview/check-strip.mjs`) measures the strip with no child at all, so it does not cover a third-party child. **Before a third-party or unreviewed card is put in either list, do one of:**
mount each region's children inside a nested element with its own shadow root (so a child's light-DOM style stays inside it), or run the browser check with that card mounted. This is an
integration decision for the second tab (design document, section 16.4), not something this proof does.

## Design notes

- Mobile first: the layout answers to the card's own width (container queries), tables become stacked rows, 44 px targets,
  visible focus rings, `prefers-reduced-motion` stops every animation and transition, light and dark follow `hass.themes`, text
  and status colours are checked against WCAG AA by the tests. Verified in headless Chrome at 375 px and 1280 px, light and dark,
  Production and Geek, on the real catalogue: no horizontal overflow.
- Performance: the DOM never holds more than one page of rows (default 25, at most 100); unchanged rows keep their node; strings,
  lists, dicts and attribute counts are capped with a visible marker.
- Source is ASCII only; every non-ASCII character is a `\u` escape.

## Recommendation: one reusable switch and adapter, not two dashboards

Roll this out to the other tabs as **this one element plus one catalogue per view**, never as a Production dashboard and a
separate Geek dashboard: the shell, the adapter, the redactor, the alert derivation and the inspector are view-independent; a view
contributes only its catalogue (data, from a generator that computes the universe from code) and its child cards. Suggested order:
Overview, Controls, Advanced. Before the second tab, split `tools/geek_mode_coverage.py` into a generic core and one small view
module per tab (see the document, section 6).
