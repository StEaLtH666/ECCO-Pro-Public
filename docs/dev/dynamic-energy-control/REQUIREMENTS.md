# Dynamic energy control: requirements (traceable)

Status: **offline design record, 25 Nov 2026.** Nothing here is implemented, installed or live-proven. It turns the owner's three
requirement messages of 25 Nov 2026 into numbered, testable requirements. The owner's wording is kept where it is precise; a
duplicate is stated once and cross-referenced. The **Covered by** column is filled in as design documents, tests and live-proof rungs
are written, so every requirement can be traced to what satisfies it. An entry `sim: ...` names scenarios of the offline simulator
([sim/SIM_README.md](sim/SIM_README.md)); the simulator proves a kernel against its own model, not the inverter, so a `sim:` entry
never closes a LIVE rung; an empty cell means nothing covers it yet.

Message A is the Gentle Smart Charging closed loop with dynamic household loads, message B the shared closed-loop framework for
three modes, message C the requirement to work through the inverter's own TOU controls and import/export limits.

Verification methods used below: **SIM** offline closed-loop simulation against an independent battery/inverter model;
**REPLAY** offline replay of saved real telemetry; **STATIC** a structural check of source code or configuration (pins,
mutation-killed); **REVIEW** an independent design or safety review recorded in writing; **DOC** a published analysis with
evidence grades; **LIVE-Rn** a rung of the read-only-first live-proof ladder in [ACTUATOR_PATHS.md](ACTUATOR_PATHS.md) section 10,
each needing the owner's own separate authorisation (none is run by this work).

## A. Gentle Smart Charging, dynamic household loads (message A)

| ID | Requirement | Verification | Covered by |
|---|---|---|---|
| REQ-A1 | The Gentle charging-rate controller operates as a closed-loop system using actual battery SOC, measured net battery charging power, household consumption and the remaining time before the target deadline. | STATIC (inputs are measured signals with ages), SIM | sim: `g01_nominal` |
| REQ-A2 | It recalculates charging progress periodically rather than relying on the original planned rate. | SIM (a deviation from the plan changes the next decision), REPLAY | sim: `g01_nominal` |
| REQ-A3 | It detects when unexpected consumption (or any other cause) makes actual SOC progress fall behind the forecast. Note: the saved nights show that at a fixed setpoint the house load is carried by the grid and does not slow the battery charge (CONTROL_AUTHORITY.md section 3), so detection must compare measured SOC and battery power with the plan, not infer a shortfall from house load. | SIM (load plus import cap, efficiency drop, taper), REPLAY | sim: `g02_heavy_overnight_load`, `g08_efficiency_drop`, `g20b_stale_frame_while_a_raise_is_due` |

| REQ-A5 | It reduces charging power when the battery is ahead of schedule. | SIM (high start SOC, better efficiency) | sim: `g01_nominal`, `g06_high_start_soc`, `g09_efficiency_gain` |
| REQ-A6 | It uses smoothing and hysteresis so that short-lived loads do not cause constant rate changes. | SIM (2-5 minute load bursts cause no change; changes per night within the budget) | sim: `g04_load_removal`, `g05_kettle_spikes` (bursts of 7 minutes seen at one plan tick: one change, no flapping; a burst of 2 to 5 minutes between two plan ticks is not seen by the planner at all and is the dongle's guard's concern) |
| REQ-A7 | It respects the inverter's **verified** charge-rate semantics, grid-import limits, BMS limits and battery protections; a setpoint path whose semantics are not verified is not used for control. | STATIC (path gated on its proof rung), LIVE-R4, LIVE-R5 | sim: `g03_heavy_load_import_ceiling`, `g10_taper_cliff_98`, `g11_unit_ac_watts`, `g12_unit_dc_watts`, `g15_unbound_response`, `g15b_charge_floor_weak_response`, `g35_power_ceiling_lowered` |
| REQ-A8 | It maintains the configurable finish-early buffer, normally 60 minutes: the deadline is the window end minus the buffer. | SIM | sim: `g01_nominal` |
| REQ-A9 | It explicitly reports when the target cannot be reached within the available power and time constraints; the target is never lowered to hide it. | SIM (infeasible nights give an at-risk or unreachable status with a reason code) | sim: `g03_heavy_load_import_ceiling`, `g07_low_start_soc_tight`, `g36_slow_tail_outside_the_world`, `g34_target_guard_hands_back`, `g34b_target_guard_reports_missed_target`, `g21b_stale_end_then_collapse`, `g23b_restart_then_collapse`, `g26b_plan_lost_then_collapse`, `f03_fixed_unreachable` |
| REQ-A10 | The test scenarios include heavy overnight loads, sudden load removal, high starting SOC, low starting SOC and changes in charging efficiency. | STATIC (the suite names each scenario), SIM | sim: `g02_heavy_overnight_load`, `g04_load_removal`, `g06_high_start_soc`, `g07_low_start_soc_tight`, `g08_efficiency_drop`, `g09_efficiency_gain`, `g16_target_already_reached` |
| REQ-A11 | The charging-rate controller is separate from the intelligent target-SOC decision engine: the target SOC is an input and the rate controller never changes it. | STATIC (no write path from the rate controller to the target; Intelligence stays SHADOW) | |

## B. Shared dynamic energy control (message B)

| ID | Requirement | Verification | Covered by |
