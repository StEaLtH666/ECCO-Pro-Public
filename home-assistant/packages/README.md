# Home Assistant packages

ECCO's Home Assistant packages: helpers, template sensors, scripts, schedules, System Health, the supervision heartbeat and the
fallback status / operator wrappers. They are plain YAML that you deploy yourself (see `deployment/ha-manifest.yaml` for the
deployable set).

Entity ids use the default device slug `ecco_clock_dongle` and the tariff entities use `your_*` placeholders. If your
installation differs, render a site copy with `tools/ecco_site_render.py` (see `ecco_site.example.yaml`) and deploy that copy.

## Reserve floor read-back

`ecco_reserve_floor_status.yaml` (read only; offline, NOTHING INSTALLED) reads back what the inverter's own registers say about the battery reserve and says whether they agree with the reserve ECCO uses. The floor is the larger of the battery shutdown SOC and the LOWEST target SOC among the non-charging TOU slots (a slot is non-charging only if its charge source reads exactly None; the charge slot is never counted; the slot targets count only while the inverter's Time Of Use flag reads on). It is compared with the plan's effective reserve (`sensor.ecco_plan_effective_reserve`). It reads the dongle's configuration read, about once a minute, and writes nothing.

| Entity | Values | Meaning |
|---|---|---|
| `sensor.ecco_reserve_floor_status` | MATCH, BELOW, ABOVE, PENDING, UNREADABLE | the floor equals, is below, is above the effective reserve; PENDING: a lease, a restore, another write, an open recovery, an ECCO TOU editor Apply in flight, or a configuration read older than 150 s; UNREADABLE: any input that is missing, unavailable, unknown, not a whole percent, not a charge source the firmware writes, or a read stale for more than 1800 s. Attributes: the floor, the slot floor, the shutdown SOC, the effective reserve, the difference, `mismatch`, the slots counted and left out, the TOU flag, the configuration read, a `reason` in words, every input with its freshness, and a constant `behaviour` note |
| `binary_sensor.ecco_reserve_floor_registers_below_reserve` | on / off / unavailable | "the registers read below the reserve, or cannot be read": on only for BELOW and UNREADABLE (device class problem); off for MATCH, ABOVE and PENDING, which means "no warning now" and nothing more; unavailable while the status cannot be read. Named for what it reads, not for what the battery does (the friendly name stops at "Reserve" because Home Assistant derives the entity id from it; the `meaning` attribute carries the rest) |
| `input_boolean.ecco_tell_me_reserve_floor_registers` | on / off | the owner's opt-in for ONE persistent notification (fixed id `ecco_reserve_floor_registers`) when the binary sensor has been on for 10 minutes; no initial value, a new helper reads off |
| `sensor.ecco_reserve_floor_core` | one text | internal: the whole rule as one record of ten fields; nothing else should read it |

The binary sensor, the helper and the notice were renamed before any install (ids persist once installed): the first draft called them "not held by the inverter" and "not enforced", which implied an enforcement that proof R6 has not shown. No id, name, notice title or notice text uses the words held, holds or enforced.

**NOT BUILT: the behavioural check.** The check that would watch what the battery does (on grid, no lease running, SOC under the floor, discharge over 150 W for 5 minutes: NOT HOLDING) was NOT built. Nothing here observes behaviour, so the binary sensor off means "no warning from the registers" and never "the reserve is enforced"; until proof R6 is run, and until such a check exists, the reserve is software only.

**Charging slots are listed, not judged.** A slot with charge source Grid, Generator or Grid + Generator is left out of the floor, so with slot 1 on Grid at 40 percent and a reserve of 80 the other slots can still MATCH. The status attribute `charging_slot_targets` lists each charging slot as slot, source and target, and every MATCH, BELOW and ABOVE reason says "charging slots not judged". Note for the owner: on a Deye time-of-use table a slot's target is inferred to act as the discharge floor of that slot whether or not charging is ticked, which is the same open question as proof R6; if it is true, a charging slot's low target is a floor below the reserve that this package does not count.

**Two time limits.** The dongle's Configuration Online flag reading off for more than 1800 s (its `last_changed`; the firmware can fail one block while the other publishes a fresh time with online false) reads UNREADABLE, and so does any single PENDING cause (a lease, operation-in-progress or snapshot flag, the editor's in-flight latch, an open recovery state) that has lasted more than 6 hours. A busy cause explains a wait, so a lease with a lost configuration read stays PENDING until the 6 hours. Home Assistant resets `last_changed` at a restart, so both limits count only continuous Home Assistant uptime (a stated limit, not a defect). No reason text carries an age, so a long UNREADABLE writes no row a minute.

A register is not behaviour: that a floor register reads a number does not prove that the battery stops at it. Whether a slot's target SOC acts as a discharge floor is the open question of proof R6, which has not been run, so the package makes no claim of enforcement and never uses the words held or enforced as a state. On the house today the non-charging slots read 0 percent, so the honest answer is BELOW: the reserve is a software value only. While a Prepare for power cut reserve runs the effective reserve is the larger value and the read-back says BELOW until the registers are raised (a later step).

There is no DRIFT state: a DRIFT verdict (the floor changed while no ECCO edit explains it) needs a reliable fact, and none exists in Home Assistant (the editor's write-seen latch stays on after an Apply, its result text carries no time, a restart resets `last_changed`, and a template entity keeps no memory). BELOW and ABOVE are the mismatch states.

Fail safe: nothing is guessed (an unreadable input is UNREADABLE, a merely late read is PENDING) and a restart, reload or outage creates no verdict by itself. The configuration time is a naive local-time text that Home Assistant reads in the Core process time zone, the same assumption as the TOU editor's freshness check. It reads no forecast, no Solcast and no Intelligence entity, and needs the plan package, the TOU target SOC editor package and the dongle entities. Recorder footprint (an ESTIMATE, not measured): about 0 to 2 rows an hour per entity in steady state, two rows per entity at every template reload; the live count needs the row-counting tools extended with the new entity ids. The notice says the reserve is software only until proof R6 has been run. Install: copy the file, check the configuration, then reload Template entities, Input booleans and Automations (Developer tools, YAML; never "reload all"); no restart (`restart_required: false`).

## Dongle lost during a lease

`ecco_dongle_lost_alert.yaml` (read only; offline, NOTHING INSTALLED) tells the owner when a Free Power or Dump to Grid lease (or the restore a half-made start still owes) was reported and the dongle's telemetry has then stayed offline for 5 minutes: ONE persistent notification (fixed id `ecco_dongle_lost_in_lease`) says in plain words that no firmware guard may be running (a Dump then exports with no Stop SOC, Free Power keeps charging to 100 percent) and what the owner can do (the inverter's vendor app: Zero Export for a Dump, the usual time-of-use table for Free Power). The second automation, `ecco_dongle_lost_alert_clear`, dismisses it when the telemetry returns. It prevents and ends nothing.

Five minutes is longer than the Dump's own 90 second fail-closed bound and than the longest dip measured on a real core for reconnects and reloads (about 70 seconds), and well inside the 15 minutes after which ESPHome restarts a dongle that has no Home Assistant client. Every trigger is a change FROM `on` (one of the six lease flags to unavailable, or the telemetry flag to off or unavailable while a lease flag reads on). The six lease flags are, for each of Free Power and Dump to Grid, Active, Operation In Progress and Snapshot Valid: the last two matter because a start that failed half-way leaves them on with Active still off (the firmware commits the snapshot before its first write and sets Active only after a verified start), so a dongle lost in that gap can leave a register or the slots changed with a restore owed and no guard running. The wait ends at once when telemetry reads on or when all six flags read off: a restart, a reload, an unavailable-to-on transition, a lease flag that reads off and an entity that did not exist never create it, and a countdown dies with a restart (a dongle lost while Home Assistant restarts is not announced). The only service calls are `persistent_notification.create` and `persistent_notification.dismiss`. Recorder footprint (an ESTIMATE): about 0 rows an hour while the dongle is healthy; the live count needs the row-counting tools extended with the new entity ids. Install: copy the file, check the configuration and reload the Automations (no restart, `restart_required: false`).
