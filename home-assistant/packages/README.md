# Home Assistant packages

ECCO's Home Assistant packages: helpers, template sensors, scripts, schedules, System Health, the supervision heartbeat and the
fallback status / operator wrappers. They are plain YAML that you deploy yourself (see `deployment/ha-manifest.yaml` for the
deployable set).

Entity ids use the default device slug `ecco_clock_dongle` and the tariff entities use `your_*` placeholders. If your
installation differs, render a site copy with `tools/ecco_site_render.py` (see `ecco_site.example.yaml`) and deploy that copy.

## Time trust

`ecco_time_trust.yaml` (read only; offline, NOTHING INSTALLED) turns what the dongle already publishes into one explicit timing-safety input. ECCO acts on time on three clocks: Home Assistant
starts schedules on its clock, the dongle ends every lease and checks every start against its NTP time, and the inverter switches its TOU slots on its own clock, which the dongle corrects
against NTP about twice an hour and which stalls for 60 s about 85 times a day. If trustworthy time cannot be established, anything that depends on it must fail safely. This package
builds the input only: it writes nothing and reads none of its own consumers, and only the packages of the READERS allow-list of its suite (`home-assistant/tests/test_ecco_time_trust.py`) may read them: the start gate and the Free Power time guard of the next step (`ecco_start_gate.yaml` and `ecco_lease_guard_free_power_time.yaml`, post-export entry `sgt1`; neither is installed nor live-proven). Any other package that mentions this one fails that suite until it is added to the list; wiring the input anywhere else is a separate step with its own approval.

| Entity | Values | Meaning |
|---|---|---|
| `sensor.ecco_time_trust_ha_clock` | TRUSTED, DEGRADED, UNTRUSTED, UNKNOWN | Home Assistant's clock against the dongle's NTP time text |
| `sensor.ecco_time_trust_dongle_ntp` | TRUSTED, UNTRUSTED, UNKNOWN | the dongle's NTP time: synced, and the text still advancing |
| `sensor.ecco_time_trust_inverter_clock` | TRUSTED, DEGRADED, UNTRUSTED, UNKNOWN | the inverter's clock against NTP, with the RTC correction health |
| `sensor.ecco_time_trust` | the same four | the worst of the three (ranked TRUSTED < DEGRADED < UNKNOWN < UNTRUSTED, so UNKNOWN never reads better than DEGRADED); attributes: the three states, `ha_clock_skew_s`, `inverter_difference_s`, `reasons` |
| `binary_sensor.ecco_time_trusted_for_leases` | on / off | lease ends and schedule starts: the dongle NTP is TRUSTED and the HA clock is TRUSTED or DEGRADED |
| `binary_sensor.ecco_time_trusted_for_ha_schedules` | on / off | Home Assistant's own schedules: the HA clock is TRUSTED or DEGRADED and the dongle NTP is TRUSTED |
| `binary_sensor.ecco_time_trusted_for_slot_edits` | on / off | the slot-time edit gate: the inverter clock is TRUSTED |
| `binary_sensor.ecco_time_trust_rtc_stall_sustained`, `..._rtc_correction_stuck` | on / off | the two debounced flags the inverter rule uses (internal) |
| `binary_sensor.ecco_time_trust_ntp_text_readable`, `..._inverter_text_readable` | on / off | on while the text is readable; their `last_changed` is the moment the text last became readable, which the LIVE condition measures against (internal) |

Eleven template entities in all, and nothing else (no automation, helper, script, trigger, action or service call). Every per-clock sensor has a `reasons` attribute, a list whose entries each start with the verdict they support. A clock is the worst of its rules.

**Freshness is judged by the values.** Home Assistant resets a state's `last_changed` on a restart and on every reconnect of the dongle's API (ESPHome re-sends its cached states on subscribe, so a copy of any age arrives
"now"), so a text that merely arrived recently proves nothing. Each dongle text therefore has to pass three conditions, and only the first is the proof; the other two can only withdraw trust:

| Condition | Rule | Verdict when it fails |
|---|---|---|
| VALUE (the proof) | the time the text carries lies within 600 s of Home Assistant's clock: 300 s of freshness (five missed publications or reads) plus the 300 s by which Home Assistant's own clock may be off before it reads UNTRUSTED. For the NTP text that is \|now() - text\| <= 600 s; for the inverter it is the age of the read, \|now() - (inverter text - difference)\| <= 600 s (the inverter text minus the clock difference is the NTP time at which the read was made, on the right date) | UNKNOWN (a stale copy and a Home Assistant clock that is far off cannot be told apart; in the second case the HA clock reads UNTRUSTED and every consumer is off) |
| LIVE (an extra) | the text changed more than 10 s after its helper (`..._ntp_text_readable`, `..._inverter_text_readable`) last changed, that is after the text last became readable: the first value after a restart, a reconnect or a dongle boot is the copy that was re-sent, not a publication | UNKNOWN until the next publication (about a minute when the dongle is alive, never when its read path is dead) |
| ARRIVAL (an extra, the earlier rule) | the text changed within the last 300 s (`last_changed`): it notices a frozen text after 5 to 6 minutes, sooner than the value bound can | UNKNOWN for the HA clock and the inverter, UNTRUSTED for the dongle NTP (a frozen text) |

A text is a time only in the exact form the firmware writes it, `YYYY-MM-DD HH:MM:SS` (`strptime` with that format): Home Assistant's own date parser also reads a date alone, no seconds, a `T`, fractions and an offset, and none of those is a time here.

| Clock | Rule (constant, and why) | Verdict |
|---|---|---|
| HA clock | skew = Home Assistant's clock when the dongle's NTP text arrived (its `last_changed`) minus the text, whole seconds. Not `now()` minus the text: that carries the text's age (up to about 60 s, more when a publication is late). The VALUE rule does not apply to this sensor (the value of the text is the skew); LIVE and ARRIVAL do | \|skew\| <= 120 s TRUSTED (the bound R9's capture accepts; about the 2 minutes of clock error that requirement REQ-D1 of the draft dynamic energy control requirements allows any use of time of day), <= 300 s DEGRADED (the firmware's `kLargeErrorS`), more UNTRUSTED, however large |
| HA clock | the text unreadable, not a time, not changed for more than 300 s, or not live | UNKNOWN (it cannot be compared; not an accusation of Home Assistant) |
| Dongle NTP | the dongle's NTP Synced flag, the text a time (not "Waiting for NTP" or "NTP time invalid"), and the text passing ARRIVAL (published every 60 s: five missed publications; the proxy for the sync age the dongle does not publish), VALUE and LIVE | all TRUSTED; any off, not a time or frozen UNTRUSTED; any unreadable, or failing VALUE or LIVE, UNKNOWN |
| Inverter clock | \|difference\| (inverter minus NTP): 60 s is the RTC monitor's trip level, 120 s the tolerance REQ-D1 gives any use of time of day | <= 60 s TRUSTED, <= 120 s DEGRADED, more UNTRUSTED (a whole hour, 3600 s, or half a day, 43200 s, included) |
| Inverter clock | failed corrections since boot > 0, or maximum clock error since boot > 120 s (the monitor's trip conditions; both latch until the dongle reboots, however large the counter) | DEGRADED |
| Inverter clock | the stall flag on for 3 minutes 30 seconds of continuous ON (a `delay_on` of 00:03:30: the flag is evaluated once per 60 s read, so four consecutive reads of it ON, an episode of 240 s, trip it and three, 180 s, do not; 210 s lies between them so the timing of the reads cannot decide, and it is 1.75 times the longest episode in the saved data: the flag is on for 60 s, a few 120 s, about 85 times a day) | DEGRADED |
| Inverter clock | a correction in progress for 5 minutes of continuous ON (the firmware releases the lock at 90 s and Home Assistant alerts at 180 s; it skips the regular clock read while a correction runs) | UNTRUSTED |
| Inverter clock | the dongle's NTP not synced (the difference is measured against it), or the inverter time text not a time, not changed for more than 300 s (the clock is no longer being read, and the last difference stays in place), or failing VALUE or LIVE | UNKNOWN |

**Fail safe.** Any input that is missing, unavailable, unknown, not a number (or not finite) can never produce TRUSTED: the clock reads UNKNOWN (or worse), the overall state is at best UNKNOWN and the three
consumers read off. The consumers are allow-lists; a consumer must test `is_state('binary_sensor.ecco_time_trusted_for_leases', 'on')` and never "not off" or "not unavailable". A restart, a template reload, a reconnect or a
dongle outage creates no trust: it makes inputs unreadable (UNKNOWN), and every value that comes back, a cached copy included, has to pass VALUE and LIVE again before a clock can read TRUSTED. The one thing it can do is restart the two debounce
counts, which delays a trip by at most its delay.

**The time-zone assumption** (the one R9 already makes). The dongle's NTP text is its local time and carries no offset; `as_timestamp()` reads such a time as local time in Home Assistant's own zone, so the two
zones must be the same. If they differ the skew reads as whole hours and is UNTRUSTED, never TRUSTED, and the dongle NTP and the inverter clock read UNKNOWN (their texts are an hour from Home Assistant's clock: the VALUE rule), so
slot edits are off too. The repeated hour of the autumn clock change reads one hour wrong (the repeated local time is read as its first occurrence): the HA clock is UNTRUSTED for that hour and the other two UNKNOWN, which fails safe.

**Replay of the saved 10 days** (15 to 25 Nov 2026; the real package run through the offline model against a saved history export, format `ecco-ha-history/1`, kept outside the repository; counts only). The
history records a state change of the clock difference, not every read: 10,140 recorded reads. **Four inputs of this replay are inferred, not recorded.** Three counters have no recorded row before 22 Nov (failed corrections, maximum clock error,
NTP synced) and are held at the values the unbroken counters imply (no dongle reboot in the window: 0 failed, at most 77 s, synced). The export has no row of the inverter time text either, so the replay feeds a SYNTHESIZED one, a fresh text
every 60 s and none during the 4 outages: a fourth inferred input. The 300 s arrival rule, the VALUE rule (the synthesized text is consistent with the recorded difference by construction) and the LIVE condition of the inverter time text are therefore not exercised by real data, only by that
synthetic feed, and the inverter-clock counts below rest on it. The NTP time text is not in the export and is left out, so the HA clock and the dongle NTP clock are not replayed (their rules are proven against a model in the suite).
Result: **10,112 reads TRUSTED, 16 DEGRADED, 12 UNKNOWN, 0 UNTRUSTED**; 14,800 of the 14,820 minutes TRUSTED. The 16 DEGRADED reads are exactly the reads above 60 s (largest 71 s), each a single read lasting at most 73 s: the longest DEGRADED run is 1 read.
The 12 UNKNOWN reads are the first read of the file and the read 49 s later (no text has changed yet since it became readable) and, at each of the 4 recorded outages of the dongle, the read at the outage, the first read after the return (within a few seconds, inputs still arriving) and, for
two of the outages, one more read within a minute (the first text after a return is the copy that was re-sent, so the clock waits for the next one: the LIVE condition, here an effect of how the synthetic text restarts); UNKNOWN lasted 64 s at most and 5 minutes in all. With the three counters left missing
(strict) the first 7 days read UNKNOWN by design: 3,188 TRUSTED, 5 DEGRADED, 6,947 UNKNOWN. The stall flag was on in 852 episodes, the longest 120 s and none over 120 s: **no stall episode ever came near the 210 s that trips the sustained-stall helper, so it never turned on**; a correction was in progress in 485 episodes,
the longest 24 s, so the stuck-correction helper never turned on either.

**NOT ESTABLISHED, and limits.** It checks that two clocks agree, not that either is true: a dongle whose NTP server stopped answering keeps counting on its own oscillator, its text keeps advancing and its
"synced" flag never clears after the first sync (pinned against the firmware in the suite); the freshness proxy detects a dead or frozen text, not that. A real sync age is one firmware field (a flash, approved
separately). Whether the inverter clock really stalls or the 60 s read cadence produces the stall flag (a firmware question) is not decided here: the package only classifies how long the flag stays on. The rules run when an input changes and at the start of every minute, so a frozen text is noticed 5 to 6 minutes after its last change.
The VALUE bound is a bound on Home Assistant's clock too: one that is more than about 9 to 10 minutes off (UNTRUSTED long before) makes the dongle NTP and the inverter clock UNKNOWN, and one near that edge can make them flap with the publication phase. The LIVE condition costs up to about a minute after every restart, reconnect, dongle boot or template reload (a stalled inverter clock or a skipped read can make it two).
The debounce counts: an unreadable flag does not restart a count in progress (the availability template of a binary template sensor is a super template: the count runs through the gap, so a 60 s episode followed by an outage of 3.5 minutes or more that returns ON trips the helper, which fails safe);
a restart or a template reload creates the helpers again and each takes back the state it had (on or off), so a helper that was on stays on, a count in progress restarts (a stall that began earlier is noticed up to 3.5 minutes late, a stuck correction up to 5 minutes late, and the stale inverter text and LIVE keep the inverter clock UNKNOWN meanwhile) and a helper with nothing to take back (a first installation) reads unknown, which is UNKNOWN for the inverter clock, until its delay ends.
Recalled from Home Assistant core, NOT verified on a real Home Assistant (the model of them is in the suite): that `states['<entity id>']` and its `last_changed` behave as modelled (new on a restart and on a reconnect), that a template using `now()` is re-rendered at the start of each minute, that `delay_on` restarts its count only when a changed result is delivered,
that an availability template is a super template (while it is false the state template is not rendered and an unchanged result is not delivered again when it turns true), that a binary template sensor with a delay restores its last on or off state when it is created (on a reload as on a restart), that a list attribute arrives as a list, that `strptime(text, format, default)` is Python's, and how `as_timestamp()` reads a naive datetime (as local time in Home Assistant's own zone); recalled from ESPHome in the same way: that the dongle's API sends every entity's cached state when a connection begins, the premise of the LIVE condition. Nothing is installed and no live read was made.

**Install.** One file copy to `/config/packages/ecco_time_trust.yaml`, a configuration check, then reload the template entities (Developer tools, YAML, Template entities, or the `template.reload` service): no
restart, no other package, no helper to create. The deployment manifest lists it (`restart_required: false`) and the pin chain carries it as the append-only post-export entry `ttr1`. The suite is
`home-assistant/tests/test_ecco_time_trust.py` (the real package against a model of Home Assistant's template entities, `home-assistant/tests/_time_trust_sim.py`, with independent models and mutants).

## Start gate and lease guards

`ecco_start_gate.yaml` and three lease guard files, `ecco_lease_guard_dump.yaml`, `ecco_lease_guard_free_power_time.yaml` and `ecco_lease_guard_free_power_import.yaml` (offline, NOTHING INSTALLED, nothing live-proven), are item N2 of the architecture reconciliation: ONE start gate for both functions, a guarded Free Power start bound to it, and guards that end a lease whose plan, time or supply no
longer allows it. They add no engine and no write path of their own: every start still goes through the dongle's own start button and its firmware gate, and every end through the existing END button. Each of the four files is installed (or left out) on its own: the guards are three files, not one, so that each can be authorised separately.

**The gate is SOFT.** Home Assistant gates bind only what goes through them. The dongle's own Start button (`button.ecco_clock_dongle_start_free_power_charge_now`, `button.ecco_clock_dongle_start_dump_to_grid_now`) can still be pressed from Home Assistant or by an assistant, past every check here, until a
firmware gate binds it (a flash, approved separately; architecture item N6). The Energy Actions card is NOT changed in this step: its Free Power Start still presses the dongle's start button directly (its Dump Start is guarded only where `dump_to_grid.guarded_start` is set), and pointing it at
`script.ecco_free_power_start_guarded` is a separate card change. Nothing else reads the gate yet.

| Entity | Package | Meaning |
|---|---|---|
| `binary_sensor.ecco_charge_start_allowed` | start gate | on only when a Charge Battery (Free Power) start passes every check below; attributes `reasons` and `blocked_by` |
| `binary_sensor.ecco_export_start_allowed` | start gate | the same for Export to Grid (Dump to Grid) |
| `input_number.ecco_grid_import_ceiling_w` | start gate | the owner's grid-import SAFETY ceiling in watts; no initial value; a readable 0 means NO CEILING CONFIGURED, a value that cannot be read blocks |
| `script.ecco_free_power_start_guarded` | start gate | the guarded Free Power start (below), a new start path bound to the gate |
| `ecco_lease_guard_dump_end` | `ecco_lease_guard_dump.yaml` | an automation that ends a Dump to Grid lease (below) |
| `ecco_lease_guard_free_power_time` | `ecco_lease_guard_free_power_time.yaml` | an automation that ends a Free Power lease when the time is not trusted (below) |
| `ecco_lease_guard_free_power_import` | `ecco_lease_guard_free_power_import.yaml` | an automation that ends a Free Power lease when the grid import stays above the ceiling (below) |
| `ecco_lease_guard_free_power_import_inert` | `ecco_lease_guard_free_power_import.yaml` | a second, small automation in that file: it only raises a notification, and presses nothing, when the ceiling cannot be read |

**What the gate checks** (each reads only a fact ECCO already has; the order is the order of `blocked_by`). `reasons` lists every blocking cause as `<CODE>: <text>` naming the entity and what it reads, then any `NOTE <CODE>: <text>` that does not block, with `ALLOWED: every check passed`
first when nothing blocks; `blocked_by` lists the codes only. Any missing, unavailable, unknown or non-numeric input closes the gate and is named; a consumer tests `is_state('binary_sensor.ecco_charge_start_allowed', 'on')` and never "not off".

| Code | Gate | Closes it when |
|---|---|---|
| `TIME_LEASES`, `TIME_SCHEDULES` | both | `binary_sensor.ecco_time_trusted_for_leases` or `..._for_ha_schedules` (the time trust package) does not read on |
| `TELEMETRY_OFFLINE`, `CONFIGURATION_OFFLINE` | both | `binary_sensor.ecco_clock_dongle_telemetry_online` or `..._configuration_online` does not read on |
| `TELEMETRY_STALE` | both | `sensor.ecco_clock_dongle_last_telemetry_update` (published only after a complete poll) is not a time in the firmware's form `YYYY-MM-DD HH:MM:SS` within 300 s of Home Assistant's clock; judged by the VALUE, never by its arrival (a reconnect re-sends a cached text as if it were new) |
| `FREE_POWER_ACTIVE`, `FREE_POWER_OPERATION`, `FREE_POWER_SNAPSHOT` | both | the Free Power lease, its start-or-restore transaction or its saved snapshot (the open recovery obligation) does not read off |
| `DUMP_ACTIVE`, `DUMP_OPERATION`, `DUMP_SNAPSHOT` | both | the same three for Dump to Grid: "already running or owed" for its own function, "the other function" for the other |
| `MANUAL_WRITE` | both | a manual inverter write is in progress |
| `OVERRIDE_ACTIVE`, `OVERRIDE_UNREADABLE` | Export | `sensor.ecco_plan_export_hold` reads held (a Hold battery, Skip tonight or Prepare for power cut), or anything but clear |
| `RESERVE_UNKNOWN`, `RESERVE_INVALID` | Export | `sensor.ecco_plan_effective_reserve` cannot be read, or is not a finite number from 0 to 100 |
| `STOP_SOC_UNREADABLE`, `STOP_SOC_BELOW_RESERVE` | Export | the staged Stop SOC (`number.ecco_clock_dongle_dump_to_grid_stop_soc`) is not a number from 0 to 100, or is below the effective reserve (refused, never changed) |
| `REVISION_UNREADABLE` | Export | `input_number.ecco_plan_revision` is not a whole number from 0 up |
| `IMPORT_CEILING_UNREADABLE` | Charge | `input_number.ecco_grid_import_ceiling_w` reads unknown, unavailable or nothing: it cannot be told whether a ceiling is configured, so the gate closes (a configured ceiling that cannot be read must not switch the check off); a readable 0 is the only "none configured" |
| `IMPORT_HEADROOM`, `IMPORT_UNREADABLE`, `REQUEST_UNREADABLE`, `IMPORT_CEILING_INVALID` | Charge | only with a ceiling configured: the staged request plus the measured grid import (never below 0) exceeds the ceiling, the import or the request cannot be read, or the ceiling is a value that cannot be one (text, negative, nan, infinite, below 1 or above 100000) |

**The import ceiling.** `input_number.ecco_grid_import_ceiling_w` has no initial value, so a fresh helper reads 0: the check reports `NOT_CONFIGURED` (a note in `reasons`: `NOTE IMPORT_NOT_CONFIGURED: ...`), does not block and says so. ONLY a readable 0 means "none configured": a ceiling that reads unknown, unavailable or missing (the helper not created yet, an input_number domain that failed to load after a restart) closes the gate with `IMPORT_CEILING_UNREADABLE`,
and the import guard stays inert but says so (below). The ceiling is a safety ceiling, never a target: the most the grid may supply at the moment (the main fuse or the supply agreement). Configured, the gate refuses `request + max(import, 0) > ceiling`, with the import read from `sensor.ecco_clock_dongle_ecco_grid_power_ct_clamp` (the dongle's CT reading, positive = importing). No charger-loss factor and no margin is applied (none is established: control-authority rung R5 measures them),
so a request that just fits can still breach by the charger's losses; the in-lease import guard ends a lease on a measured breach. A value that cannot be a ceiling (text, negative, nan, infinite, above 100000, below 1) closes the gate rather than switching the check off.

**The guarded Free Power start** (`script.ecco_free_power_start_guarded`) is the analogue of the guarded Dump start, which presses the start button only after its checks. It tries once (a manual start has no retry loop) and its order is: validate the request; read the gate (a closed gate refuses before anything is staged; a gate closed only by `IMPORT_HEADROOM` or `REQUEST_UNREADABLE`
is judged again after an explicit request is staged); stage the power and then the duration with `number.set_value`, only a value that differs from what is staged; arm the write enable and wait up to 5 s for the dongle to confirm the arm and both values; read the gate again; press the start button once; wait for the dongle's answer.
Optional fields `power_w` and `duration_minutes` stage a request the way the scheduled start does; with neither it starts the request already staged on the dongle, as the card does. The result text is `input_text.ecco_plan_last_result`, the one the guarded Dump start writes: `REFUSED <CODE> - <text>` for a refusal,
`FAILED <CODE> - <text>` after a press that did not start Free Power, `STARTED free_power at <P> W for <D> min (guarded start).` on success, with one persistent notification (`ecco_free_power_start_blocked`). It does not use the Free Power schedule's result text: that text belongs to the schedule's state machine (its status sensor, retry loop,
R9 recovery and alert read its prefixes) and the start bypass detector reads `STARTED OK - <n>W for <m> min` in it as the proof of a SCHEDULED run, which a manual start must not forge or overwrite.

Two rules about what a run leaves behind. **The write enable:** this run turns it off at the end only if THIS run turned it on. A write enable that was already on when the run began (armed by the schedule or by a card user) is left as found, a refusal before the arm touches nothing, and the firmware itself disarms the switch at a press. **The staged request:** a refusal at the press-time check after an explicit request (`GATE_CLOSED`, `SCHEDULED_START_RUNNING`, `NOT_CONFIRMED`, `LIMIT_LOWERED`)
writes back, once and then confirmed by the dongle's readback, the power and the duration this run replaced, and says in the result text and the notification what stands: "The staged request was put back to ...", or, when that could not be confirmed (or the staged value could not be read before the run), exactly what the dongle held before and holds now. A start with no explicit values changes nothing, so there is nothing to put back.

| Code | Meaning |
|---|---|
| `GATE_UNREADABLE`, `GATE_BLOCKED` | the gate cannot be read, or is closed (the blocking codes are named); nothing staged, armed or pressed |
| `SCHEDULED_START_RUNNING` | a scheduled Free Power start is running or cannot be read (before the stage), or began meanwhile (at the press-time check) |
| `LIMIT_UNREADABLE`, `LIMIT_OUT_OF_RANGE` | the effective grid charge limit cannot be read (the text says what it reads); or it is readable but outside the supported 500 to 100000 W (the text says the value) |
| `POWER_INVALID`, `DURATION_INVALID` | the power is not a multiple of 100 W from 500 W to the limit; the duration is not a whole number of minutes from 1 to 240 (a staged value that cannot be read is printed as "unreadable") |
| `GATE_CLOSED`, `NOT_CONFIRMED`, `LIMIT_LOWERED` | the press-time check: the gate closed while the request was staged, the dongle did not confirm the arm and the values within 5 s, or the limit fell below the request or can no longer be read; nothing is pressed and the staged values this run replaced are put back |
| `FIRMWARE_REFUSED`, `START_FAILED`, `NO_ANSWER` | after the press: the dongle's own gate refused it (nothing written), a start transaction began but Free Power did not become active (the firmware restores its saved snapshot itself), or the dongle did not answer (unconfirmed, never retried) |

Two things it does not do. The start bypass detector (bpd1, pinned) knows only the scheduled run's `STARTED OK` and the guarded Dump start as ECCO's own records, so a start made by this script is recorded by the detector as a start with no ECCO record, a BYPASS (the incident record and counter are written; a popup only when an override is active or a plan reading
is unreadable); teaching the detector about it is an edit of a pinned package and is not made here, and the card should not be pointed at the script before that edit. And smr1 puts the owner's request numbers back only after a SCHEDULED start: a start with explicit values that is refused is put back by the script itself (above), one that starts replaces the owner's staged request and nothing restores it (a start with none changes nothing).

**The lease guards** each need the owner's separate install authorisation, read nothing from one another and stand alone (each is its own package file with its own manifest entry; the suite proves that each ends its lease with the other two absent). Each only ever presses an existing END button, then raises one persistent notification that says what was ended and why, and pauses for a minute
(one violation, one press). They start, arm and write nothing. The Free Power side is two automations, not one, because each counts its own delay and a run that is counting drops every trigger that arrives meanwhile (mode single).

| Guard | Ends | When | Constant and why |
|---|---|---|---|
| `ecco_lease_guard_dump_end` | Dump to Grid, `END DUMP TO GRID - RESTORE NOW` | `sensor.ecco_plan_export_hold` turns to held (a Hold battery, Skip tonight or Prepare for power cut; a change from the sensor's own value `unknown`, a record it could not read, counts, one from `unavailable` or from nothing does not), or the effective reserve changes, or the lease turns active, and the reserve is above the Stop SOC the lease latched (`sensor.ecco_clock_dongle_dump_to_grid_active_stop_soc`) | the latched sensor updates every 5 s, so a lease that has only just turned active is waited for up to 15 s; the dongle enforces only the latched Stop SOC, so nothing else ends a lease when the reserve rises |
| `ecco_lease_guard_free_power_time` | Free Power, `END FREE POWER - RESTORE NOW` | `binary_sensor.ecco_time_trusted_for_leases` changes from on to off while a lease is active, or a lease turns active while it reads off (an unavailable, unknown or missing sensor is not a reading), and it has not read on for 5 minutes | the lease ends on the dongle's own NTP time; 5 minutes is more than the LIVE condition costs after a reconnect (about a minute, two at worst) and more than the 3 minutes 30 seconds stall debounce, so a reconnect or restart alone never ends a lease |
| `ecco_lease_guard_free_power_import` | Free Power, `END FREE POWER - RESTORE NOW` | a ceiling is configured and the measured grid import stays above it for 30 seconds while a lease is active | three 10 s polls: a short confirmation, not an average; with a ceiling of 0 the guard is inert, and with a ceiling that cannot be read it is inert too but its notice automation says so in one notification (`ecco_lease_guard_free_power_inert`) when a lease has been active for a minute with the ceiling unreadable |

**The Free Power press is the operator's End.** In the firmware `END FREE POWER - RESTORE NOW` is not an ordinary request: pressed while a lease has a saved snapshot, it sets the one-shot "an operator pressed End or Retry THIS time" flag (`free_power_operator_retry_pending`), which `restore_free_power_snapshot` consumes as an explicit operator request, and an explicit request clears the durable operator-decision lockout and resets the retry backoff and the
verify-mismatch count (`end_free_power_button`; pinned in the suite). Pressed while a restore is owed, blocked or locked out, it would therefore re-authorise unattended writes against a condition no human has seen. So a Free Power guard presses it ONLY for a lease it has verified to be running normally, judged after its wait, just before the press: no start or restore in progress (`binary_sensor.ecco_clock_dongle_free_power_operation_in_progress` reads off, not unavailable or unknown); the status text starting `ACTIVE - VERIFIED OK` (the firmware's own text after a verified activation; every other text it publishes refuses, whatever it says: `END REQUESTED`, `END DEFERRED`, the `RESTORE`, `RECOVERY`, `OPERATOR DECISION`,
`ACTIVATION VERIFY`, `FORCE`, `ACCEPT`, `REJECTED`, `STARTING` and `START FAILED` texts, `Inactive` and the rest; the suite reads the vocabulary from the firmware and refuses each text in turn); an end time in the future (`sensor.ecco_clock_dongle_free_power_ends_at`, read in the firmware's exact form against Home Assistant's clock; a lease that is past its end, or whose end cannot be read, is the dongle's own watchdog's); and END not pressed since the lease turned active. The last rule is the shared once-per-lease marker: the END button's own state is the time of its last press, and a press by either guard or by the operator since the lease began stops every further guard press, so the two Free Power guards press at most once per lease between them. A guard that does not press changes nothing and raises
one notification (`ecco_lease_guard_free_power_declined`, shared by both) that says why. The notification of a press (`ecco_lease_guard_free_power_ended`, shared) says that this press is the operator's End. The marker uses the time the lease flag last changed, which Home Assistant resets at a restart and at a reconnect of the dongle: a lease that was re-announced counts as beginning then, and the status check is the line of defence behind it. A press does what END always does: the dongle restores the exact values it saved before the lease.
The Dump guard needs none of this: `request_dump_end` only sets the restore request, `restore_dump_to_grid_snapshot` still refuses while the operator lockout stands (only Force Restore Original bypasses it) and the End press does not reset the backoff, so the Dump END is not an operator retry (pinned in the suite too); the dongle records the end reason of a guard's Dump press as "manual End button".

A guard acts only on a positive reading: a hold that reads held, a reserve and a latched Stop SOC that are both numbers, a time-trust sensor that was on and now reads off (or reads off when a lease starts), an import that is a number above a configured ceiling. A restart, a template reload, a reconnect and a boot never end a lease by themselves: every trigger must be a change from a reading (not from unavailable, unknown or nothing; the one exception is the hold sensor's own `unknown`, above), nothing runs at the Home Assistant start, and a count in progress dies with
a restart. A violation that already stands when Home Assistant starts is not acted on until the next change; a measured import breach that persists after the entities return is still ended after its 30 seconds (it is a fact about the supply, not about the restart). The guards are SOFT: Home Assistant down, a dead dongle or a press the dongle does not act on ends nothing, and they do not retry.
There is no target-reached guard for Charge Battery in this step.

**Follow-ups, not built here** (each is its own step with its own approval): (1) a target-reached guard for Charge Battery: item N2 also asks for a Free Power END when the target is reached, and nothing here ends a Charge Battery lease at a target (the lease runs to its end time or to the operator's End); (2) the card wiring: the Energy Actions card's Free Power Start still presses the dongle's start button directly, and pointing it at `script.ecco_free_power_start_guarded` is a card change, to be made only after (3); (3) the start bypass detector (bpd1, pinned) records every guarded Free Power start as a bypass (its counter goes up, and a popup is raised when an override is active) until a pinned edit teaches it the script; (4) the firmware gate (item N6), without which every Home Assistant gate stays soft; (5) an automatic END with no operator authority is a firmware option (a separate flash) and not something a Home Assistant guard can offer.

**Install.** `ecco_start_gate.yaml`: copy the file to `/config/packages/`, check the configuration, then reload the input_number helpers first (so that the gate does not read a ceiling that does not exist yet), then the template entities, then the scripts (Developer tools, YAML), one at a time, never "reload all"; no restart. It needs `ecco_time_trust.yaml`, `ecco_plan_helpers.yaml` and the two schedule packages (without them the gate reads off and the script refuses).
Each guard file: copy it, check the configuration, reload the automations; no restart; each is installed or left out on its own. The Dump guard needs the plan sensors; the Free Power time guard needs `ecco_time_trust.yaml` (it is one of the two packages on that package's READERS allow-list); the Free Power import guard needs the ceiling helper of `ecco_start_gate.yaml`; without a source a guard stays inert. Delete the file and reload the same domains to remove any of them.

Recalled from Home Assistant core and not verified (the model of them is in the suite): that a state trigger carries `trigger.from_state` (none for an entity that did not exist), that `to: ~` fires on a change of the state and never on an attribute alone, that a template trigger fires on false to true and is not armed while already true, that `wait_template`
with `continue_on_timeout` continues at once when its template is already true, that `mode: single` with `max_exceeded: silent` drops a trigger while a run is busy, that a list rendered by an attribute template arrives as a list, that a script field that was not given reads as undefined, that a button entity's state is the time of its last press (and is restored across a restart), that `states['<entity id>'].last_changed` is the time of the last change of the state, and that `as_timestamp` of a time with no offset reads local time in Home Assistant's own zone. ## Export coordinator

`ecco_export_coordinator.yaml` (offline, NOTHING INSTALLED, nothing live-proven) is item N3 of the architecture reconciliation, version 0. It is a **READ-ONLY SHADOW**: nine template sensors and nothing else, built on MEASURED values, that propose the three things Home Assistant chooses when it starts an Export to Grid (Dump to Grid) lease (the Stop SOC, the net export target and the duration) and, while a lease runs, report how the live lease compares and whether a change WOULD be allowed. It has no automation, script, helper, trigger or service call and writes nothing to the dongle or the inverter. Only the control state read model (`ecco_control_state.yaml`, a display) reads the sensors. The dongle's own Dump closed loop already adapts the battery power to the house load inside a lease (settle at least 45 s, +-150 W deadband, at most 120 writes a lease), so Export needs no new firmware and no in-lease actuator; this package only proposes what to start.

**The gates are soft.** The dongle's own Start button (`button.ecco_clock_dongle_start_dump_to_grid_now`) bypasses every Home Assistant check, this one included, until a firmware gate binds it (a flash, approved separately; architecture item N6). A VALID proposal is not permission to start.

**Which start the numbers are for.** The SCHEDULE path: the Stop SOC, the export power and the window (its start and its length) of the Export schedule's own helpers, which is what a scheduled start stages (it raises the Stop SOC to the effective reserve, rounded up). The Stop SOC staged on the dongle (`number.ecco_clock_dongle_dump_to_grid_stop_soc`) is NOT read: it is a leftover of the last manual or scheduled run, kept across restarts, and it never enters the floor, except as the latched value of a RUNNING lease (below). A manual or guarded start uses the values the owner staged; the coordinator proposes nothing for it, and a running lease that the schedule did not start is reported UNKNOWN (`LEASE_ORIGIN_UNKNOWN`), never judged against the schedule's numbers. The Stop SOC a running lease latched (`sensor.ecco_clock_dongle_dump_to_grid_active_stop_soc`, published only while a lease runs) is a raise-only member of the floor while that lease runs, so the proposal is never below what the running lease enforces (`FLOOR_FROM_RUNNING_LEASE` names it; one that cannot be read while a lease runs makes the proposal INVALID, `LEASE_STOP_SOC_UNREADABLE`); it is also compared with the proposal and used for END NOW. Who started a lease is inferred (the scheduled start script's last run, the window, the lease's own end), not recorded: a manual start that turns on within 15 minutes after a scheduled run that started no lease (it was blocked, failed or cancelled), inside the window, would be taken for the schedule's lease and compared with its numbers (shadow only; the schedule's last-result helper would tell and is not read).

| Entity | Meaning |
|---|---|

| `sensor.ecco_export_proposal` | `VALID`, `INVALID`, `UNVERIFIED`, `HOLD` or `NOT ALLOWED` (a VALID proposal that the Export start gate does not allow), with `reasons` (every blocking cause named with the entity and what it reads), `blocked_by` (the codes; for `NOT ALLOWED` the gate's own), `actionable` (true only for a VALID proposal while the gate is open and has been for 60 s: information, never permission), `notes`, the raw requirement, what limited it, the schedule window end (`window_end_ts`) and, labelled as what the dongle's own loop would do, `loop_battery_power_w` and `loop_duration_min` |

Every numeric proposal sensor is UNAVAILABLE (never 0) unless the proposal itself is `VALID` or `UNVERIFIED` (its state is then `VALID`, `UNVERIFIED` or, while the start gate does not allow a start, `NOT ALLOWED`: the numbers describe the proposal, they are not a permission); a consumer tests `is_state('sensor.ecco_export_proposal', 'VALID')` and never "not INVALID". No attribute carries a time that moves with the clock (the proposal's end is now plus its duration), so the proposal, the re-target and the comparison publish again only when a number or a text changes. The model carries no time of its evaluation either (decision D-C04a, route a), so with unchanged inputs nothing is published at all.

**The rules.** (1) The floor is the largest of the schedule's Stop SOC, the effective reserve of the plan package, the dongle's own minimum and, while a lease runs, the Stop SOC that lease latched, rounded up: never below any of them. (2) The energy is `max(0, SOC - floor - 1 point) / 100 x capacity x 0.90` (`DISCHARGE_EFFICIENCY`, a flat figure: see the efficiency below), from the measured SOC and the battery capacity helper (the smaller of it and the capacity the battery runtime package has measured). (3) The net export is the configured target kept below the Max Grid Export less the dongle's START headroom, `max(100 W, 3 %)`: **an export limit is a safety ceiling for the target, never the target.** The expected battery power is `clamp(net export + measured house load - measured PV, 0, min(power ceiling, supervised-proven level))`: measured PV only, no forecast entity is read anywhere (the suite pins it, and the exact attributes it reads from every entity). A PV surplus the target cannot hold is never VALID: `TARGET_INFEASIBLE_LOW` (the measured PV exceeds the house load by more than the net target plus the loop's 150 W deadband: the dongle shows TARGET INFEASIBLE LOW and never commands battery charging) and `PV_SURPLUS_EXPORT_GUARD` (that surplus plus the 500 W the loop never goes below is above the Max Grid Export less the START headroom: the dongle's export guard would end the lease). (4) The duration is the energy over that power (never below the dongle's 500 W command floor, which also keeps the division defined), **bounded by the schedule's own window** and rounded DOWN to the minute: the window is the schedule start helper plus its duration helper, and, while now is inside it, the duration is at most `floor((window end - now + 20 s) / 60 s)` minutes, exactly as the schedule caps a run, so a proposal never ends after the window end (plus the schedule's own 20 s rounding) and a re-target never moves a lease's END beyond it; before the window a start at its own time may run the whole length and after it the next window will, when no lease runs. **While a lease runs the same bound holds at every render, after the window end too: a running lease gets no time past the end of the window it runs in** (the duration is 0 and the proposal INVALID, `BELOW_MINIMUM_DURATION`, as in the last 10 minutes of any window, until the lease ends; the next window is for the next start, not for a run still going, and the schedule fixes a run's end at its start plus its length, so a run pressed in the first 20 s of its window ends up to 20 s after the window end). **For a lease the schedule started the bound is min(window end, the lease's own latched end) + 20 s**: the lease's own end is the window captured at its start, so editing the schedule's duration or start helper while it runs cannot move it later (an edit that brings the window end before the lease's own end moves the bound earlier, which only gives less). Under 10 minutes is not worth a start and is INVALID (in the last minutes of the window no start fits); an unreadable window start is INVALID (`SCHEDULE_START_UNREADABLE`). (5) `HOLD` while a Hold battery, Skip tonight or Prepare for power cut is active, with no number at all; `INVALID` while any blocking cause stands (a missing, unavailable, unknown, non-numeric, non-finite, negative or implausible input, stale telemetry, the dongle's limits not VALID, the Max Grid Export not configured, a floor the dongle cannot take, a PV surplus the target cannot hold, no energy above the floor); `UNVERIFIED` when holding the target would need more battery power than the supervised-proven level and the dongle's Power Ceiling lets its loop go above it (the 8000 W setpoint behaviour is an unresolved control-authority question): the proposal stays clamped to the proven level, and the expected loop power at `min(raw requirement, Power Ceiling)` and the duration at that power are published beside it as `loop_battery_power_w` and `loop_duration_min` (what the loop would do, not a proposal and not proven). (6) The re-target is a shadow, judged only for a lease the SCHEDULE started (the scheduled start script last ran at most 15 minutes before the lease turned on, the lease did not turn on more than a minute before the window start and does not end more than two minutes after the window end); for any other lease it is UNKNOWN with `LEASE_ORIGIN_UNKNOWN`, and so is the comparison. A change is reported as allowed only after 30 minutes of lease, not within 30 minutes of the previous would-change and **not until the memory that says so is itself 30 minutes old** (a template reload starts it afresh: `MEMORY_YOUNG`; a restart does not, because it restores the model's state and attribute, so the 30 minute rules continue across it, lab D3, decision D-C04d; `this` may be none, undefined or a state object with no attributes, and each of them waits), and only beyond a deadband (the floor 1 point above the Stop SOC the lease latched, the net export by 200 W either way, the energy lasting 20 minutes or more beyond the lease's end, inside the window), and only while `binary_sensor.ecco_time_trusted_for_leases` (the leases consumer ONLY) reads on and has read on for 60 s, else WAIT with `TIME_NOT_TRUSTED` (no time to wait for: the dongle ends a lease on its own NTP time); a re-target could only ever be the END of the lease plus a guarded re-START, at most one per 30 minutes, and never a write by Home Assistant into a running lease. **For a lease the schedule started the END rule never fires**: its proposed end is bounded by its own latched end plus 20 s (rule 4), so the END part of a re-target can only keep the end or shorten it, never move it later, and a shorter end is no deviation either (a lease that would end by its Stop SOC before its end time needs no change); the Stop SOC raise and the export target change are unaffected, and the END rule stays in the package as a second line. **END NOW** is the lease guard's rule, outside the 30 minute rules: while a lease runs (whatever started it) and a Hold battery, Skip tonight or Prepare for power cut reads held, or the effective reserve is above the Stop SOC the lease latched, the state is END NOW, never WAIT; nothing acts on it (the lease guard, not installed, is what would press END). An end time that reads before now or before the lease start, in a skipped hour or in a repeated hour (the second 01:xx hour when the clocks go back) is not read: UNKNOWN, never ALLOWED. An UNKNOWN re-target lists no changes. (7) **`NOT ALLOWED`** replaces `VALID`, and only `VALID`, while `binary_sensor.ecco_export_start_allowed` does not allow a start now: it reads off with a cause (its `blocked_by` codes, cut to 40 characters, become the proposal's own), it cannot be read (`GATE_UNREADABLE`: missing, unavailable, unknown, or a list that is not a list), its state and its list disagree (`GATE_INCONSISTENT`), or it has read on for less than `GATE_SETTLE_S` = 60 s (`GATE_SETTLING`: at a restart or a reload the entity exists with a restored or a fresh state for a moment, and a state that young is not trusted; the age is that of its STATE, an attribute that changes alone does not renew it). The numbers stay, they describe the proposal; `actionable` is true only for a `VALID` proposal with no gate code. A `HOLD`, `INVALID` or `UNVERIFIED` proposal is never replaced: its own causes stay in `blocked_by`. The constants and their reasons are in the package header (`MAX_TELEMETRY_AGE_S`, `DISCHARGE_EFFICIENCY`, `SOC_MARGIN_POINTS`, `MIN_COMMAND_W`, `MIN_DURATION_MIN`, the origin tolerances and the others).

**Rounding and rows (CS-06).** The published powers (the proposal's power, the loop's power and the raw requirement) are rounded UP to a multiple of 500 W, never above their clamp (the proven level for the proposal, the Power Ceiling for the loop); the duration is worked out at the rounded-up power and published rounded DOWN to a multiple of 5 minutes (10, the minimum worth a start, is one), so a published duration is never longer than the exact one (at 3 kW up to about 14 % shorter, a cost in exported energy and never in safety). The safety decisions (the floor, the Stop SOC, the reserve, the limits, the clamps, UNVERIFIED, the PV surplus rules) are taken on the unrounded readings, and the minimum duration on the whole minutes at the rounded-up power. The live export of a running lease and its difference from the proposal are published rounded to 100 W (the re-target decision stays on the exact difference); the battery ceiling the dongle commands moves only with the dongle's own steps (at least 45 s apart), and the two counters in whole minutes (the lease's age and the END difference) move once a minute. While a lease runs and its live export wanders 100 W a poll no template-only rounding goes below about 360 rows an hour for the model, 210 for the re-target and 300 for the comparison (probe, offline), so the exclusion matters most then. Offline probe (10 s polls, one simulated hour, a house load wandering up to 150 W a poll, 800 W start): model, proposal and shadow comparison 353 rows an hour before and 61 after; power 353 and 61; duration 327 and 61; a calm house (one poll in ten moves the load) 40 before and 7 after. `actionable`, like a VALID proposal, is NOT a promise that the guarded Start runs these numbers: it runs the numbers staged on the dongle (the control state read model says so).

**The efficiency.** `DISCHARGE_EFFICIENCY` is a flat 0.90. The earlier figure, 0.92, was described as pessimistic and is not: the fit of the control authority study (AC = 0.924 x DC - 50 W) gives 0.909 at 3 kW, 0.912 at 3.8 kW, 0.88 at 1 kW and 0.84 at the 500 W floor. 0.90 lies inside the firmware's own 7-12 % DC-over-AC allowance (about 0.89 to 0.93), about 1 % below the fit from 1.9 kW up (so a duration there is a little short) and above it below 1.9 kW (a duration at a low power is a few percent long, 7 % at the floor); it is not a bound at every power, and the Stop SOC, which the dongle enforces, is what keeps the reserve. PV is credited 1:1 against the AC power (it is the DC-side measurement), which makes the expected battery power a few percent low. The package no longer says that the inverter's own shutdown SOC lies below the 10 % software guard: that is not established and the sensor is not read.

**How it relates to what exists.** It consumes the plan package's effective reserve and hold (no second reserve model), the dongle's Dump limits (the Dump limits package describes them and holds the supervised-proven level), the Export schedule's own power, Stop SOC and window helpers and the scheduled start script's last run, the canonical house power (unavailable, never 0, when stale), the battery runtime package's capacity, and the dongle's latched lease values. **Three energy figures exist and differ on purpose.** (a) The coordinator's `sensor.ecco_export_proposal_energy`: the usable energy above the floor (the larger of the schedule Stop SOC, the EFFECTIVE reserve and, while a lease runs, the Stop SOC it latched, rounded up) after the one point margin and the 0.90 efficiency. (b) The Intelligence dump advice (`intelligence/dump_advice.py`, SHADOW): a reserve-aware stop level and exportable energy from the same inputs plus a forecast-derived planned demand and a one-way efficiency of 0.949; the coordinator mirrors its arithmetic and its 10-90 % range but does not read it (it may be unavailable and is forecast-derived). (c) The battery runtime package's `sensor.ecco_battery_time_to_reserve` attribute `energy_above_reserve_kwh`: `(SOC - input_number.ecco_minimum_reserve_soc) x Wh per percent`, DC, the OWNER's reserve, no efficiency and no margin; the coordinator reads that sensor only for `capacity_kwh` and `capacity_basis`. During a Prepare for power cut (c) and (a) differ by the whole raise of the reserve. **A card that shows an export should show (a), `sensor.ecco_export_proposal_energy` with the proposed duration; (c) answers how long the house runs on the battery down to the owner's reserve, and (b) is advice only.** The Export schedule raises the Stop SOC it stages to the effective reserve and the guarded Dump start refuses a lower one; the coordinator proposes the same raised value as a floor, a short duplicate of an existing rule that the suite proves against the real plan package. The lease guard ends a lease when a hold starts or the reserve rises; the coordinator's END NOW only reports that rule.

**What it reads of the start gate and of the time trust package (slice S-A2 of the shared control integration; deliberate, design decision D-PIN).** Two pinned lists were widened for this, each by two edits a reviewer sees and each pinned by mutants (commit 0b6328b of this branch): the start gate suite's gate READERS list now lets this package read `binary_sensor.ecco_export_start_allowed` (its state and its `blocked_by` list) and nothing else of that package (not the charge gate, not the bypass), and the time trust suite's READERS allow-list now lets it read `binary_sensor.ecco_time_trusted_for_leases`, the leases consumer ONLY (not the schedules or the slot-edit consumer, not a per-clock sensor, the overall sensor or an internal helper). Both are only read and both are SOFT (the dongle's own Start button bypasses them): `actionable` is information, never permission, nothing here starts, ends or changes anything, and a consumer must still require the gate itself to read on. The widening was a coordinator decision taken as an engineering decision (design D-PIN, owner priority 1); it is not the owner decision on the Power Ceiling below, which stays open.

**Owner decision before any re-target is used: the Power Ceiling.** When the dongle's Power Ceiling is above the supervised-proven level (for example a ceiling of 8000 W above a proven level of 3000 W), every proposal that needs more than the proven level is UNVERIFIED, the re-target never evaluates (it is UNKNOWN: it lists no change), and the proposal's power and duration describe the clamp, not the loop (the loop's own figures are beside them). The owner decides, separately: (a) lower the dongle's Power Ceiling to the proven level (the proposal is then VALID and the loop's figures equal it), (b) prove the proven level and raise it (a supervised proof ladder, authorised separately), or (c) accept a shadow with no re-target data (the proposal and the comparison still run). This file decides none of them.

## Control state

`ecco_control_state.yaml` (offline, NOTHING INSTALLED, nothing live-proven) is slice S-A1 of the shared control integration: **one read model for Charge Battery and Export to Grid**, three template sensors and nothing else. It is a **display and never a gate**: no automation, script, helper, trigger, action or service call, it writes nothing to the dongle, the inverter or any entity, and no package may read it (the suite pins that no other package mentions these three entities), so it cannot become a second decision path. The card panel and the Geek Mode catalogue read it later (slices S-B and S-B2). Whether a start is allowed stays the start gate's and the dongle firmware's job, and the gates are soft: the dongle's own Start buttons bypass them. A state of `IDLE` with `start_allowed` true is not permission, it is what the gate says.

| Entity | State | Attributes |
|---|---|---|
| `sensor.ecco_charge_control_state` | `IDLE`, `PLANNED`, `ARMED`, `ASSISTED`, `RUNNING`, `ENDING`, `FAULT`, `UNKNOWN` | `why` and `next_action` (one fixed sentence each), `blocked_by` (codes), `start_allowed`, `start_path`, `end_path`, `lease` (the end-time text, the staged power and duration), `notes` (closed codes) |
| `sensor.ecco_export_control_state` | the same | the same (`lease` with the staged export target, duration and Stop SOC), plus `proposal` (the export coordinator's state and `blocked_by`, `used_by_guarded_start` (always false) and its note, the floor and the net export; `NOT_INSTALLED` while the coordinator is absent, unavailable or unknown, never an error), `retarget` (its state, the kinds of change, its reason codes; END NOW says that no END guard is installed: press END) and `facts` (the hold and what holds it, the effective reserve, the Stop SOC the lease latched against it, the Dump limits state and the Power Ceiling against the proven level, all as words or settings) |
| `sensor.ecco_control_owner` | `NONE`, `CHARGE`, `EXPORT`, `MANUAL_WRITE`, `RESTORE_OWED`, `UNKNOWN` | `live_match` (always `NOT_READ`: the saved profile's Live Match is not read here, see Inputs) and `note` |

**The states.** First match wins, in this order: `UNKNOWN, FAULT, ENDING, RUNNING, ARMED, ASSISTED, PLANNED, IDLE`. The dongle's lease, operation-in-progress and saved-snapshot flags decide; its status text refines. `UNKNOWN`: an input the state needs cannot be read. `FAULT`: needs the owner (a saved snapshot waits for a restore and nothing runs, the status text says a restore or recovery is blocked, failed or waiting for a decision, both leases read active at once, or the lease reads active and the status does not confirm that it is running normally). `ENDING`: the lease is being ended and the saved settings restored. `RUNNING`: the lease is active and the status says `ACTIVE - VERIFIED OK` (a raw Start press that the firmware refused during a healthy lease leaves a `REJECTED` text until the END: the lease still runs, `RUNNING`, with the note `LAST_PRESS_REFUSED`; Export to Grid says only that the dongle loop works toward the net export target and ends the lease at the latched Stop SOC, and the loop's own word is a note, `LOOP_SETTLING`, `LOOP_TRACKING`, `LOOP_SATURATED_LOW`, `LOOP_SATURATED_HIGH`, `LOOP_TARGET_INFEASIBLE_LOW`, `LOOP_TARGET_INFEASIBLE_HIGH`, `LOOP_NO_RESPONSE` or `LOOP_OTHER`). `ARMED`: a start is under way (the write enable is on, a start script runs, or the dongle reports a start in progress; both start paths publish the ACTIVE text before they clear the operation flag, and that moment is ARMED, never ENDING). `ASSISTED` is RESERVED, no function reads it today: it is for a start that runs a proposal of ECCO or the request the owner staged. Export to Grid never reads it, because the guarded Dump start runs the numbers STAGED on the dongle, not the coordinator's proposal (that is for the schedule path), until the slice S-C1 binds the Start to the proposal; Charge Battery would use it for the Free Power request the owner staged and has no proposal yet. `PLANNED`: the schedule is armed. `IDLE`: nothing runs, nothing is owed.

**`start_allowed`** is true only when the function's gate reads on with an empty `blocked_by` list AND the time trust reading for leases reads on AND the other function's lease, operation and snapshot flags and the manual write flag all read off (one that reads on while the gate reads open is named in `blocked_by` and `why`, never "nothing is running") AND the state is `IDLE`, `PLANNED` or `ASSISTED`. It is never true while the gate is off, while time is not trusted, while any input is unreadable (the read model is then `UNKNOWN`) or in any other state, and `why` says so in plain words (`Not ready: ...`). Every sentence is fixed and from a closed list (the suite pins each one, and that none has a digit): a measured number never appears in a sentence. `blocked_by` lists `UNREADABLE_<INPUT>` for every unreadable input, then the gate's own codes (the gates' number-bearing `reasons` are NOT copied), then `TIME_LEASES` when the consumer reads off and the gate does not say so, and `GATE_INCONSISTENT` when a gate's state and its list disagree (on with a cause, off with none): such a gate is never open.

**Inputs.** The state needs: the gate (state and `blocked_by`), the time trust leases consumer (`binary_sensor.ecco_time_trusted_for_leases`, the one entity of that package this file may name), the lease, operation and snapshot flags of both functions, the manual write flag, the function's status text (a text the model does not know counts as unreadable), its write enable, its two start scripts and its schedule armed helper. Everything else only fills an attribute (`NOT_READ` when it cannot be read): the end-time and request numbers, the grid import ceiling (a readable 0 is a note, `IMPORT_NOT_CONFIGURED`), the hold, the effective reserve, the latched Stop SOC, the Dump limits, both schedule status sensors, the coordinator's proposal and re-target. The coordinator's live figures (energy, duration, power) are not copied. **The saved profile's Live Match is NOT read:** the pin of `registry/tests/test_fallback_live_match.py` lets only the fallback status package, the dashboard and the HA package suites name that entity, and a third reader would be a pin widening that the design does not name; so `live_match` on the owner sensor is always `NOT_READ` and the dashboard shows the Live Match itself (a later, deliberate and pinned widening could allow it).

**The status texts** are classified by prefix into families (`ACTIVE`, `FAULT`, `ENDING`, `STARTING`, `DONE`); the suite reads every literal the firmware can publish for the two functions and requires each to land in exactly one, and a text that lands in none makes the read model `UNKNOWN`. A stale text never decides alone: with every flag off a `DONE` or `STARTING` text is just `IDLE`; only a `FAULT` text is held against the owner until the dongle publishes another.

**The one-lease rule.** The two functions never both read `RUNNING`: if both lease flags read on, both read `FAULT`, the owner reads `UNKNOWN` and nothing is startable.

**Rows.** No attribute carries a measurement, a number a gate prints in its reasons, or a time that moves: the templates never call `now()` and read no state object, so a sensor publishes a new state or attribute only when its inputs really change it, and the same inputs rendered twice (also while the gates' reasons and a running lease's status text move with every poll) give the same state and attributes and write no recorder row.

**Restart, reload and first state** (lab facts of 27 Nov on a real Home Assistant core 2026.11.0; recalled here and modelled in the suite). A template reload re-creates every template entity and, for 13 to 27 s (bound about 70 s), the time trust consumers and both gates read OFF: the read model then shows not ready with the gate's own codes. At a restart the template entities exist with their RESTORED state for tens of milliseconds before their first render: for that moment this file shows what the gate shows, and nothing may act on it, which is why nothing reads this file; anything that ever acts on a gate or a consumer must itself wait 60 s after a start. The dongle's texts are parsed in the Core process time zone; this file parses none (it shows an end-time text as it is, after a check of its form), so a wrong container zone cannot change it, and it does not use `this`.

**Notes** (closed codes, each true of the wiring at this base; the slice that changes the wiring removes its note in the same commit): `SOFT_GATE`, `CARD_START_NOT_GATED`, `GUARDED_START_NOT_GATED`, `SCHEDULE_NOT_GATED`, `RATE_FIXED_AT_START`, `NO_TARGET_REACHED_END`, `NO_END_GUARD`, `IMPORT_NOT_CONFIGURED`, `IMPORT_CEILING_NOT_READ`, `PROPOSAL_NOT_INSTALLED`, `PROPOSAL_FOR_SCHEDULE_PATH`, `SCHEDULE_LAST_RUN_FAILED`, `LAST_PRESS_REFUSED` and, for a running Export lease, the `LOOP_*` codes.

**The guarded Start and the proposal (CS-01).** The guarded Start runs the numbers STAGED on the dongle; the export coordinator's proposal is for the schedule path and is information only (the `proposal` attribute says `used_by_guarded_start` false and carries the note `PROPOSAL_FOR_SCHEDULE_PATH`, and the Export `why` and `next_action` say so in plain words). An Export that is idle with its gate open therefore reads `IDLE` with `start_allowed` true, never `ASSISTED`, and an armed Export schedule reads `PLANNED`. The suite pins that Export never reads `ASSISTED`.

**Status texts and gate readings (CS-02, CS-04).** The `DONE` family includes the Dump's `ACCEPTED CURRENT STATE -` texts (they are published on the line after `publish_state(` and fit no other family); the suite reads every `publish_state` call of the two status sensors with a balanced scan (multi-line literals, `std::string` concatenations and messages built by `snprintf`) and requires every call to land in a family. A gate that reads off with no text code in its list (an empty list, `[5]`, `[None]`) is counted as inconsistent (`GATE_INCONSISTENT`) and never as "closed ()".

**Two pins were widened, deliberately (design decision D-PIN, owner priority 1, a coordinator decision taken as an engineering decision), each exactly and only as named, each pinned by mutants.** (1) The start gate suite no longer says that no other package mentions the gate entities: it holds a READERS list, the export gate may be read by the export coordinator and by this package, the charge gate by this package, and every other package still fails (a comment naming a gate id counts as a read). (2) The time trust suite's READERS and PINNED_READERS (two copies) add the export coordinator and this package, for the leases consumer only: the schedules consumer keeps the start gate as its only reader, nobody reads the slot-edit consumer, and the per-clock and overall sensors stay unread. Adding a third reader, widening an entry or removing the clause fails the suite.

**Install** (needs the owner's go; not part of this step). One file copy to `/config/packages/ecco_control_state.yaml`, a configuration check, then reload the template entities: no restart, no helper, no other file. Install ONLY with no Dump to Grid or Free Power lease running and outside any armed scheduled Export or charge run, from its start until its window end plus 10 minutes: the template reload re-creates every template entity, the plan's hold and effective reserve sensors included, which the Export schedule's press-time recheck reads. It needs the time trust, start gate, plan helper and both schedule packages for its inputs (without them it reads `UNKNOWN` and names the missing input); the export coordinator is optional. The deployment manifest lists it (`restart_required: false`) and the pin chain carries it as the append-only post-export entry `csm1`, hash-linked after `exc1`: the entries must be sealed again with the reseal tool, in merge order, when the main chain moves (PRs 70, 72 and 74, then this one, then the reserve branch).
